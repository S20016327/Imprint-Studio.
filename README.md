# بصمة إبداع | Imprint Creative

استوديو لتجهيز منشورات الصور والفيديو وحفظها في مساحة خاصة، تمهيدًا للنشر على
TikTok وInstagram وFacebook وYouTube.

- **الموقع:** https://s20016327.github.io/Imprint-Studio./
- **الاستضافة:** GitHub Pages من الفرع `main` والمجلد `/ (root)`.
- **الخلفية:** Supabase — المشروع `Imprint Studio` (`yxmetzdoxbqndecslhlu`, `eu-central-1`).

> **تنبيه مهم:** الموقع واجهة ثابتة. النشر إلى منصات التواصل وربط الحسابات
> والجدولة الآلية **غير منفّذة**. ما يعمل فعليًا هو: تسجيل الدخول، وحفظ المسودات
> والملفات في Supabase، وفتحها وتعديلها وحذفها.

## ما تم إنجازه في هذه الجولة

### إصلاح خلل حاسم كان يعطّل الحفظ السحابي

نسخة الواجهة السابقة كانت تعرّف معالج زر «حفظ مسودة» مرتين: مرة في `index.html`
تحفظ **في `localStorage`**، ومرة في `cloud.js` تحفظ **في Supabase**. السكربت
المضمّن كان يُنفَّذ بعد `cloud.js`، فكان يطغى على المعالج السحابي. النتيجة أن زر
الحفظ لم يصل إلى Supabase في أي حالة. أُعيد تنظيم العلاقة بين الملفين، وأصبح
`cloud.js` هو المسؤول الوحيد عن الشبكة والحساب.

كما كانت حقول الدخول `disabled` في القالب القديم، ومفتاح `iframe` في `openPanel`
يستبدل عنوان اللوحة بعنوان ثابت. عولج الاثنان.

### إصلاح جوهري في طريقة المصادقة

المفتاح `sb_publishable_…` **ليس JWT**. كان الكود يرسله في `Authorization: Bearer`
عند غياب جلسة، وSupabase يرفض ذلك. الآن:

| الحالة | الترويسات المرسلة |
|---|---|
| قبل الدخول | `apikey: sb_publishable_…` فقط |
| بعد الدخول | `apikey: sb_publishable_…` + `Authorization: Bearer <توكن المستخدم>` |

### ميزات الواجهة

- واجهة عربية RTL متجاوبة بالهوية (كحلي `#031425`، تركوازي `#107177`، ذهبي، برونزي، كريمي).
- اختيار صورة أو فيديو بالسحب أو التصفح، مع تحقق مسبق من الصيغة والحجم
  (PNG، JPG، WebP، MP4، MOV، WebM — حتى ١٠٠ ميغابايت) قبل أي رفع.
- مصغّرة ومعاينة كبيرة، وشريط تقدم فعلي للرفع.
- تسجيل دخول بالبريد وكلمة المرور عبر Supabase Auth، وجلسة في `sessionStorage`
  تُمسح بإغلاق النافذة، مع تجديد تلقائي للتوكن قبل انتهائه.
- حفظ مسودة جديدة أو تحديث المسودة المفتوحة (`POST` / `PATCH` حسب الحالة).
- **مكتبة المحتوى:** عرض المسودات، فتحها بملفاتها، حذفها (مع حذف ملفها من التخزين).
- **جدول المنشورات:** عرض المواعيد المحفوظة داخل المسودات فقط.
- **الحسابات المرتبطة:** توضيح المتطلبات لكل منصة بدل أزرار وهمية.
- تصدير تفاصيل المنشور نصيًا، وتصدير الصورة الأصلية دون تعديل.
- رسائل خطأ عربية مفهومة بدل رسائل Supabase الخام.
- عدّادات أحرف مطابقة لحدود قاعدة البيانات.

### قاعدة البيانات (طُبِّق فعليًا)

ترقيات على `public.imprint_posts`:

- إلغاء كل صلاحيات `anon` على الجدول (لم يكن يحتاجها).
- إزالة `TRUNCATE` و`REFERENCES` و`TRIGGER` من دور `authenticated`.
- مشغّل يضبط `updated_at = now()` فلا يعتمد على ساعة المتصفح.
- قيود تحقق: المنصات من القائمة المعروفة، الحالات المعروفة، وأطوال الحقول
  (العنوان ≤ 300، الوصف ≤ 5000، الوسوم ≤ 2000).
- فهرس `(owner_id, created_at desc)` لتسريع المكتبة.

### إعدادات المصادقة (طُبِّقت فعليًا)

- `site_url`: كان `http://localhost:3000` ← أصبح `https://s20016327.github.io/Imprint-Studio./`
- `uri_allow_list`: رابط الموقع وفروعه، مع `localhost:3000` و`localhost:5173` للتطوير.
- `disable_signup`: ما زال `true` (الاستخدام شخصي).
- `refresh_token_rotation_enabled`: `true`.

## ما تم اختباره فعليًا

### اختبار عزل RLS بمستخدمين حقيقيين (على قاعدة البيانات)

أُنشئ مستخدمان مؤقتان في `auth.users`، ونُفِّذت العمليات تحت الدور `authenticated`
مع مطالبات JWT لكل مستخدم، ثم حُذف كل شيء:

```
User B:  visible_rows = 0 من صفوف A
         insert into own row      → نجح
         insert with A's owner_id → مرفوض (WITH CHECK)
         update A's rows          → 0 rows
         delete A's rows          → 0 rows
Storage: B يرى 0 كائنًا، ولا يستطيع التعديل أو الحذف في مجلد A
         insert في مجلد A         → مرفوض
```

النتيجة: **سياسات RLS وسياسة مجلد التخزين تعمل كما هو مطلوب.** جرت الاختبارات
داخل جداول مؤقتة ثم نُظِّفت (`imprint_posts` = 0، `storage.objects` = 0، `auth.users` = 0).

### اختبار الواجهة آليًا (37 اختبارًا)

```bash
npm install
npm test
```

`tests/flow.test.mjs` (27) — تشغيل الصفحة في DOM حقيقي مع شبكة موقوفة:

- الدخول: رسالة خطأ عربية لكلمة مرور خاطئة، ثم الدخول الناجح وظهور البريد.
- الحفظ: مرفوض بلا عنوان، مرفوض بلا منصة، ثم `POST` صحيح بالبيانات المتوقعة.
- **الحفظ الثاني يستخدم `PATCH`** على نفس المسودة لا `POST` جديدًا.
- الترويسات: المفتاح في `apikey` وتوكن المستخدم في `Authorization`.
- المكتبة والجدول والحسابات وتصدير التفاصيل وتسجيل الخروج.
- تجديد الجلسة المنتهية وحفظ التوكن الجديد.
- الحفظ بدون جلسة يفتح لوحة الدخول.

`tests/media.test.mjs` (10) — مسار الوسائط:

- رفض صيغة غير مدعومة، ورفض ملف أكبر من ١٠٠ ميغابايت.
- بناء مسار الرفع داخل مجلد المستخدم: `<user-id>/<uuid>.png`.
- ترويسات الرفع صحيحة، والحفظ يكتمل بعد نجاح الرفع.

`tests/check-html.mjs` — لا معرّفات مكررة، ولا `label` بلا هدف، ولا معرّف يستدعيه
الكود وغائب عن الصفحة، ولا أخطاء تحليل.

### ما لم يُختبر

- **دورة حقيقية بحساب مستخدم فعلي على الموقع المنشور.** لا يوجد أي مستخدم في
  `auth.users` حتى الآن. اختبار الواجهة أعلاه يستخدم شبكة موقوفة، لا خادمًا حقيقيًا.
- رفع ملف حقيقي كبير (قرب ١٠٠ ميغابايت) وحجم استجابة التخزين على الخطة المجانية.

## ما يحتاج تدخلك (لا يمكن تنفيذه عبر الموصلات)

### ١) إنشاء حسابك — هذا ما يمنع أي اختبار حقيقي الآن

التسجيل العام مغلق (`disable_signup = true`) وجدول `auth.users` فارغ. أنشئ المستخدم
من لوحة Supabase:

**Authentication ← Users ← Add user ← Create new user**، وأدخل بريدك وكلمة مرور
(٦ أحرف على الأقل) وفعّل **Auto Confirm User**، ثم ادخل من زر «تسجيل الدخول» في
الموقع. لا ترسل كلمة المرور في المحادثة.

### ٢) تدوير المفاتيح وكلمة مرور قاعدة البيانات

في الجولة السابقة ظهرت كلمة مرور قاعدة البيانات المؤقتة ومفتاح `service_role`
القديم في سجل أدوات المحادثة. الحالة الحالية: **المفتاحان القديمان `anon` و
`service_role` ما زالا نشطين** (ينتهيان في 2036)، ولم يتأكد تنفيذ التدوير.

الإجراء المطلوب منك:

1. Supabase ← Settings ← Database ← **Reset database password**.
2. Settings ← API Keys ← إنشاء مفتاح `secret` جديد وحذف المفتاح `service_role` القديم.
3. إذا كان المفتاح `anon` القديم قد استُخدم في أي مكان، أنشئ `publishable` جديدًا
   وأبلغني لتحديث `cloud.js` (المفتاح المنشور آمن للعرض، لكن القديم يجب إبطاله).

لا تحفظ أي مفتاح سري في GitHub — ملفات الموقع عامة.

### ٣) متطلبات النشر الفعلي على المنصات (المرحلة القادمة)

النشر الحقيقي يحتاج خادمًا لا GitHub Pages:

- **TikTok:** تطبيق مطوّر معتمد، OAuth، ومراجعة صلاحيات النشر.
- **Instagram / Facebook:** تطبيق Meta، حساب أعمال مربوط بصفحة، ومراجعة App Review
  لصلاحيات النشر.
- **YouTube:** مشروع Google Cloud مع YouTube Data API وحصة نشر كافية.
- تخزين رموز الوصول وتجديدها على الخادم فقط، مع وظائف مجدولة (`pg_cron` أو
  Supabase Edge Functions + Scheduler) تسجّل حالة كل منصة: نجاح أو فشل أو إعادة محاولة.

الوسوم والعنوان والوصف تُكتب يدويًا كما طلبت؛ **لا يوجد تحليل فيديو أو ذكاء اصطناعي
في المنصة**، ولا تُضاف إلا بطلب صريح منك.

```

cloud.js     Supabase: الجلسة، المسودات، الوسائط، اللوحات، رسائل الخطأ
tests/       اختبارات آلية (jsdom) للتدفقات والوسائط والبنية
```

`index.html` و`cloud.js` كافيان للنشر. لا حاجة إلى `.github/workflows` مع النشر من
الفرع.

## الأمان

- لا يوجد في المستودع أي مفتاح سري. `cloud.js` يحتوي المفتاح القابل للنشر فقط،
  وهو مصمم للعرض العلني.
- الحماية الفعلية تأتي من RLS: كل صف مرتبط بـ`auth.uid()`، وكل ملف في مجلد يحمل
  معرّف المستخدم، والـ bucket خاص.
- الصفحة نفسها عامة؛ لا تضع فيها بيانات لا تريد نشرها.
